# Design: PageIndex-style vectorless RAG

Retrieval by navigating a document's table-of-contents tree with an LLM agent, instead of embedding similarity (vector RAG). Inspired by PageIndex (VectifyAI). Not the IBM "STAIR" paper, which is a trained generative retriever and a different approach.

## Product
A public portfolio web app. Visitors bring their own API key (BYOK) for Anthropic, OpenAI or Google Gemini, choose the two models from the list their key can use, upload documents in the UI, and chat over their whole library. Each answer shows text with citations, a clickable source view, images inline, and the agent's navigation path (streamed live). A visitor's library lives on the server for the length of their session only (no accounts). A pre-indexed sample library is browsable without a key; chatting needs a key. The CLI is a small dev tool, not part of the product.

## Scope (v1)
- Inputs: PDF and Word (.docx) (plus Markdown), with or without a ToC.
- No OCR for now (scanned PDFs are out of scope; revisit later).
- Documents without a ToC get one generated by the app.
- Library-level chat from the start: the agent picks a document, then descends its tree. Multi-turn, with history.

## Data location and safety
- Libraries live on the server, in a per-session folder of JSON files (no database). Nothing is saved in the browser. The folder is deleted when the session ends (best effort; check whether Reflex exposes a disconnect hook) and a sweep deletes any session older than 2 hours (this is the guaranteed path).
- Uploads: strictly `.pdf` and `.docx`. Check content, not just the name: a PDF must start with `%PDF-`; a docx must be a zip containing `word/document.xml`, with a cap on uncompressed size as a zip-bomb guard. `.zip`, `.doc`, Markdown and everything else are rejected in the UI (Markdown stays for the dev CLI and tests).
- Sample library: 3 pre-indexed documents in `samples/index`, read-only, shared by all sessions, never touched by the sweep. Sources are in `samples/source`, built by `scripts/build_samples.py`.
- The visitor's key lives only in session memory; never written to disk, logs or saved indexes. Show a cost estimate before indexing.
- Public-app limits: per-session isolation, file size and page caps, upload type checks, zip-bomb guard, rate limiting, sanitized rendering of document text.

## Indexing pipeline
1. Extract structure, cheapest first, stop at the first believable result:
   - Word: paragraphs with an outline level (what Word's Navigation Pane lists: Heading 1-9 and most custom heading styles) give the tree directly, no LLM. Content controls are read like normal content. A Word-inserted ToC is kept out of the text, its entries stored as `source_toc`; it is not needed for the tree, being generated from the headings. A typed contents page (`indexing/typed_toc.py`, any file type): found near the start (3+ lines ending in a page number), levels from numbering or indentation (from each page's own left edge; entries named like chapters, "I." or "Chapter 3", go a level above the rest), each entry found in the body in order (a short paragraph with the same text, numbering ignored, or up to 3 short paragraphs that together give it), in a PDF only on the page its number points to (by printed page label, else with the offset most matches agree on; one page of slack, exact page first), trusted only if at least 2 and at least half are found; a list of figures is skipped. A trusted one is removed from the text and kept as `source_toc`; it builds the tree only when there are no headings. When neither gives an outline: lines formatted like headings (`indexing/heading_looks.py`): short, mostly words rather than numbers (a chart's axis labels are not titles), not ending like a sentence (a question is fine), standing out (all bold, bigger than normal text, numbered like a section, capitals), not captions or Word list items. Only a look that recurs (3+ times, 2 in a short document, with text between) counts: a pull quote or one big title stays text. Given up if those lines hold over 30% of the text or two thirds of the paragraphs. Levels from numbering, else by look, at most 3. Else the text is cut by size. The index records which built the tree (`structure_source`: headings / typed_toc / formatting / none). The same detector also runs inside a section too big to read (documents built from headings or a typed contents page, with splitting on): a look that appears at least twice in that section, with text between, gives its sub-headings, one or two levels below it, before anything still too big is cut by size. A one-off bold line there stays text.
   - PDF (`indexing/pdf_extract.py`; pypdfium2 + pdfplumber, both permissive: PyMuPDF is AGPL, ruled out): lines grouped into paragraphs by gap and look, each keeping its font size, boldness and page; running headers, footers and page numbers removed first (margin lines recurring on many pages, numbers aside). Figures found first (`indexing/pdf_layout.py`): areas dense with drawn shapes are charts, rendered to PNG as images (so the vision model can describe them and answers can show them) with their labels left out of the text; a framed box holding sentences is not a figure (its frame is peeled off and the inside searched again); a ruled grid with mostly filled, wordy cells is a Markdown table; embedded pictures are cut out the same way (icons and page backgrounds skipped). Two text columns are read left then right. A figure is cited by its own page. Bookmarks give the tree when believable (2+, mostly real titles, junk like "Page 3" dropped), each heading placed at the line carrying its title. Else the same detectors as Word: a typed contents page, then lines formatted like headings, then size cuts. Refused with a reason: password-protected, scanned (no text layer on most pages), over the page limit (300, checked before reading). LLM-parsed contents pages and LLM-generated structure come later.
   - Any file: refused if its extracted text is over a cap (500k tokens), since text, not file size, is what costs time to index.
2. The original ToC is only a base. Keep it as data in `source_toc`; the navigable tree is our own refined one.
3. Refine the tree carefully (`indexing/refine.py`). Each tree level costs the agent one tool call, so the tree should be shallow, and the original ToC changes only where a section breaks a limit. A good ToC comes back unchanged. All of these are free (no LLM) and each can be turned off:
   - Split a section too big to read in one go (`max_leaf_tokens`, default 2000). First look for its own sub-headings (lines formatted like headings, see step 1); then cut what is still too big at the best boundary: paragraph, then sentence, then a hard cut. A big table is cut between rows with its header repeated. Parts are balanced and an image stays with its paragraph. Parts get a free title from their first sentence (LLM summaries re-title them). A document with no headings becomes one level of parts under the root, never deeper.
   - Small sections (`small_sections`): `merge` (default) joins runs of tiny sibling leaves (under `min_leaf_tokens`, default 150) into one section titled "A · B · C", and makes a section whose only content is one subsection absorb it ("A › B"). The root only absorbs a lone child that has subsections, so a document always keeps an outline. `fold` also turns any subtree small enough to read in one go into one section. `off` keeps the ToC exactly. Merged and folded titles go in `location.covers`, so citations still name them.
   - Mark nodes `origin: original | generated`.
4. Summaries, as the options ask (`IndexOptions`, presets in `indexing/options.py`):
   - Free: no LLM. Every section shows a preview (its first sentences, plus "Covers: ..." for its subsections). No key needed.
   - Budget: short LLM summaries (one or two sentences), no image descriptions.
   - Full (default): detailed LLM summaries, bottom-up (a parent's summary is built from its children's summaries), and image descriptions. Summaries should say what questions the section answers.
   - The UI shows the cost of each preset before indexing, plus an advanced panel with every single option.
5. The agent's listing can show 2-3 levels at once (`agent_listing_depth`, default 2; deeper levels show titles only), so it can jump to a deep section without a call per level. This changes nothing in the tree.
6. Tables: extract as Markdown text, keep whole inside their node (unless a table alone is too big to read in one go), mention them in the node summary.
7. Images: a vision model writes a description and tags at index time. Images with a side under 32 px (icons, rules) are skipped; the test is pixel size, not file size, because a flat-colour chart is a tiny file. Large images are shrunk to 1568 px before sending (API limit is 5 MB).

## Data model
Node: `id`, `title`, `summary`, `text`, `children`, `origin`, `location`.
- Text is normalized to plain strings. Citation info lives in `location`, separate from the text.
- PDF location: page range, with printed page number and PDF page index kept separate (show users the printed one). Pages travel through the tree as markers in the text, so a split part or merged section gets its own range (`indexing/pages.py`).
- Word location: heading path (no stable pages).
Image record: `id`, `description`, `tags`, `location`, file path. Searchable like any other node content.
Library: a root node whose children are documents, each with a one-paragraph summary.

## Agent (LangGraph)
- Tools: `list_documents`, `open_document`, `list_children`, `read_node`, `go_up`. A one-document library starts with that document open.
- The loop ends the standard way: the model replies in plain text with no tool call. Sources are inline markers, `[doc_id:node_id]` and `[img:doc_id:img-1]`, parsed out of the reply. A marker becomes a citation only if the section exists and the agent read it with `read_node`. Same format a vector-RAG baseline can use, so the two stay comparable.
- Loop: choose a document and branch, read, judge whether it answers the question; if not, `go_up` and try another sibling or open another document.
- Citations and image ids are qualified: `doc_id:node_id`, `doc_id:img-1`.
- `stream_agent` yields a `Step` per navigation action (for the live path), then the final `AnswerResult`. Prior turns are passed as `ChatTurn` history.
- State keeps a visited set so branches are never retried.
- Step budget (about 10-15). On exhaustion, say the answer wasn't found rather than guess.
- May pick 2-3 branches at one level for ambiguous questions.
- Answers cite the node's location.

## Stack
- UI: Reflex (Python). Indexing is its own module and must not import Reflex.
- Agent: LangGraph.
- Storage: JSON files per document to start; SQLite once there is a library.
- LLM: Anthropic, OpenAI or Google Gemini through LangChain (`langchain-anthropic`, `langchain-openai`, `langchain-google-genai`); everything provider-specific is in `providers.py`. The rest uses LangChain's common interface: tool calls, structured output, image input.
  - The visitor picks the provider, then pastes a key. Checking the key = listing the models it can use (free). The visitor then picks both models (indexing, chat) from that list: nothing is pre-selected and the code names no models, so nothing goes stale. Chat waits for a chat model; indexing with summaries or image descriptions waits for an indexing model.
  - Two roles. Indexing (summaries, split titles, image descriptions; later ToC parsing/generation): a small, cheap model. Agent (branch choice, judging, final answer): a stronger one that supports tool calling.
  - The dev CLI and the sample builder take their models from `PAGEINDEX_INDEX_MODEL` and `PAGEINDEX_AGENT_MODEL`.
  - Tight output caps on summaries only for Anthropic: OpenAI and Gemini models may spend output tokens on hidden reasoning first, so they get a generous cap.
  - Errors and refusals are recognised for all three (LangChain's standard error types, HTTP status, each provider's refusal signal).
  - Use prompt caching for the repeated tree prefix in agent calls.
  - Validate Haiku summary quality on a real document before committing.

## Staging
1. Library-level agent (done)
2. Reflex app: BYOK key entry, upload and background indexing with cost estimate, chat with live path, citations, source panel, images, sample library (Word/Markdown). Built and verified end to end in real Chrome with an offline fake model (`tests/e2e/run_e2e.py`, 38 checks). Not yet tried with a real Anthropic key. Needs Node 22.22 or newer (Reflex 0.10)
3. Tree refinement and indexing options (done): split / merge / fold, presets Free / Budget / Full with live cost estimates, free previews, multi-level agent listings. `samples/index` is rebuilt with it (Full preset, real key).
4. Model providers (done): Anthropic, OpenAI and Google Gemini keys, provider picker, both models chosen by the visitor from the key's live model list (no defaults). Verified with unit tests and the offline model; not yet run against real OpenAI or Gemini models.
5. PDF: steps 1-3 done (paragraphs, bookmarks, running headers and footers, page ranges and printed page numbers, refusals, page and text caps; charts and pictures as images, ruled tables, two columns; typed contents pages checked against page numbers). Next: a page-image source view. LLM-generated ToC (off / only when missing / always) comes with this stage, for Word too.
6. Session storage, 2-hour expiry sweep, limits, deployment, prompt caching
7. OCR / scans (later)

## Future work
- LLM-assisted splitting: an option where the LLM picks topic boundaries inside an oversized section (and titles the parts) instead of size-based cuts.
- LLM-generated ToC for documents with no ToC or a poor one (see stage 3).
- Sub-heading detection inside big sections (bold, numbering, font size) before cutting by size.

## Open questions
- Thresholds: max 2000 / min 150 tokens and listing depth 2 are starting defaults; tune them with the eval below.
- Library layer: grouping when there are many documents; cross-document questions.
- Eval: compare against a plain vector-RAG baseline on accuracy, tokens, latency.
